複数案件の要望から次の開発を提案するAIエージェント

複数案件に散らばった顧客要望を集約し、「次に何を作るべきか」の提案レポートを返す AI エージェント。 本資料では、誰がいつ使い、何が入力され、何が出てくるのかを実装前に確定させる。

1. 何を解決するか

1つのサービスを複数の案件（顧客）に提供していると、要望は案件ごとにバラバラに集まる。 言い方が違うだけで中身は同じ要望が並び、売上規模や契約状況も案件ごとに異なるため、 「どれから着手すべきか」の判断に毎回時間がかかる。

背景: 複数案件を並行して見る業務で、要望の読み合わせと優先度整理に毎回時間がかかっていた。 その経験から、入力データをもとに整理と提案までを自動化する題材を選んだ。

解決したいこと

  • 要望が案件ごと・入手元ごとに分かれており、横断で比較できない
  • 「CSV出力がほしい」「一覧をExcelで落としたい」のように、表現が違う同じ要望が重複して数えられる
  • 売上規模や契約状況を踏まえた判断が属人的になり、再現しづらい
  • 優先度の根拠が個人の記憶に依存し、他メンバーへの説明に時間がかかる
このエージェントがやること: 案件情報・要望・プロダクト情報を読み込み、似た要望をまとめ、 売上規模・顧客ランク・契約状況などから算出した重要度を踏まえて優先度を付け、 プロダクトの現状を踏まえて新規追加か既存改善かを判断し、 「どの機能を、なぜ、どの優先度で改修/追加すべきか」を根拠つきのレポートにして返す。

TypeScript の CLI から実行する業務ツールとして作る。 判断材料を揃えるところまでを担当し、最終的な採否と実装計画への反映は人が行う。

2. ユーザーと使う場面

主ユーザー

プロダクトマネージャー（PdM）。 複数案件を並行して見ており、週次の優先度会議や次スプリントの計画前に、 要望を整理して着手候補を決める立場の人。

副次的に、営業・CS が「自分の案件の要望がどう扱われているか」を確認する用途も想定する。

使う場面

週次の優先度会議の直前。これまで手作業で要望を並べ直していた 1〜2 時間の準備を、 レポート生成と確認に置き換える。

タイミング これまで 導入後
会議前の準備 各案件の要望を手作業で読み、スプレッドシートに転記して並べ替える CLI からエージェントを実行し、出てきたレポートを確認・修正する
優先度の説明 「重要顧客からの声なので」と口頭で補足する 関連要望と、売上規模・顧客ランク・契約状況等の案件属性が根拠として明記されている
会議後 議論内容をあらためて整理し直す 採用した提案をバックログへ登録する（人が行う）
AI に任せる価値があるのはどこか: 売上規模・顧客ランク・契約状況からの重み付けはルールで書ける。 一方、 表現の違う要望を同じテーマとしてまとめること、 プロダクト情報を踏まえて新規追加か既存改善かを判断すること、 提案内容を人が読める文章にすることはルールでは書きづらく、ここに実行時の LLM API を使う。

3. スコープ

3.1 このプロダクトが担う範囲

  • 案件情報・要望データ・プロダクト情報の読み込み
  • 要望のテーマ分類と、意味が近い要望のグルーピング
  • 売上規模・顧客ランク・契約状況から重要度を算出し、優先度付けに反映する
  • プロダクト情報を踏まえた新規追加 / 既存改善の判断と、根拠の提示
  • レビューに使えるレポートの出力・保存

3.2 担わない範囲

対象外 理由
要望の収集・入力そのもの 営業・CS の既存業務。既に蓄積されたデータを入力として受け取る
採否と実装計画への反映 人が判断する。誤った提案がそのまま実装計画に入るのを防ぐ
作り込んだ Web UI 今回は業務フローが最後まで動くことを優先する
認証・マルチテナント・本番監視 単一チームでの利用を前提とし、本格運用時の課題として切り分ける
このエージェントの出力は提案であり、決定ではない。 最終的な採否と実装計画への反映は人が行う前提で設計する。

4. 処理の流れ

実行してからレポートが出るまでの流れと、どこをルールで処理し、どこを AI に任せるか。

  1. 案件・要望・プロダクト情報を読み込むルール 対象期間の案件情報、それに紐づく要望、およびプロダクト情報（主な機能・方針・制約等）を取得する。件数が多い場合は上限を設ける。
  2. テーマに分類し、近い要望をまとめるAI 1要望につき主テーマ1つを付与し、必要なら関連テーマを補足する。「CSV出力がほしい」「Excelで落としたい」のように表現が違う要望を、同一テーマとして扱う。
  3. 案件属性から優先度スコアを計算するルール 売上規模と顧客ランクを初期設定で重視し、契約状況・要望件数・複数案件への広がりを補助的に加味して、テーマごとのスコアを算出する。事業上の重要度は直接入力せず、これらの項目から導出する。
  4. 改修 / 追加の提案文と優先度を作るAI スコアと要望内容、プロダクト情報をもとに、何をどう変えるかを文章化する。既存機能の改善か新規追加かを、プロダクトの現状機能と照合して区別する。
  5. レポートとして出力・保存するルール テーマ・優先度・提案・根拠をまとめ、人が読める形式で保存する。
  6. 内容を確認し、バックログへ反映する人 PdM が提案の採否を判断し、採用した内容を実装計画へ反映する。この工程はツールの外側に置く。
AI の出力をそのまま信用しない: 優先度スコアはルールで算出し、AI にはその根拠となる要望のまとめと文章化を担当させる。 AI が返す内容は決まった形式に沿っているかを検証し、崩れていた場合はやり直す。

5. 入力と出力

5.1 入力

エージェントが参照する業務データ。事業上の重要度は入力項目として持たず、下記の案件属性からルールで算出する。新規追加 / 既存改善の判断には、プロダクト情報を参照する。

データ 項目 業務上の入手元
案件 識別子、名称、契約期間、売上規模、顧客ランク、契約状況 案件管理シート、CRM、社内マスタ
要望 識別子、対象案件、要望本文、入手元、日時（任意で緊急度） 営業・CS のヒアリング、定例議事録、問い合わせ
プロダクト情報 現在提供している主な機能、各機能の説明、プロダクト方針、今期重視していること、既知の開発上の制約 プロダクトロードマップ、機能一覧、PdM / 開発チームの社内資料

「入手元」は要望が記録された経路（定例、問い合わせ等）を示す。案件ごとに分かれた要望を、案件 ID で紐付けて横断的に扱う。 プロダクト情報は、要望が既存機能の改善なのか新規追加なのかを判断するための参照データとする。

5.1.1 データの扱い（サンプル同梱時 / 実務利用時）

区分 データ 保管・共有 目的
サンプル同梱時 GitHub リポジトリ上の架空データ（案件・要望・プロダクト情報） リポジトリに同梱し、第三者が API キーを設定すれば実行できる状態にする デモ・検証。顧客情報を含まない
実務利用時 実際の顧客データと生成レポート GitHub や Google ドライブなど、社内限定の共有環境で管理する 週次優先度会議の準備など、本番業務での利用

5.2 出力

PdM がレビューと共有に使うレポート。テーマごとに次の情報を含める。

項目 内容
テーマ まとめられた要望群の名前
提案 何をどう変えるか。プロダクト情報を踏まえた新規追加 / 既存改善の区別
優先度 案件属性、要望件数、複数案件への広がりを踏まえた順位
根拠 元になった要望、参照した案件属性（売上規模・顧客ランク・契約状況等）、参照したプロダクト情報
影響案件 そのテーマに要望を出している案件

出力イメージ（1テーマ分）

テーマ
データのエクスポート機能
提案
一覧画面に CSV エクスポートを追加する（新規追加 — 現行機能一覧に該当機能なし）
優先度
高
根拠
4件の要望が該当（A社・B社・C社・D社）。うち2件は売上規模が大きく、契約更新が近い案件から。複数案件にまたがるテーマのため優先度を高めに設定。プロダクト情報の現行機能一覧に CSV エクスポートは含まれないため、新規追加と判断。
影響案件
A社、B社、D社

出力は提案までとし、チケット作成や実装計画への反映は人が行う。

6. 機能要件

ID 要件 優先度 補足
FR-01 案件一覧を読み込める Must 契約期間、売上規模、顧客ランク、契約状況を含む
FR-02 要望一覧を読み込める Must 対象案件・入手元・日時との紐付けがあること
FR-03 プロダクト情報を読み込める Must 主な機能、各機能の説明、プロダクト方針、今期重視していること、既知の開発上の制約を含む
FR-04 要望をテーマに分類できる Must 1要望につき主テーマ1つ。必要なら関連テーマを補足する
FR-05 表現が違う同じ要望をまとめられる Must 文字列の一致だけに頼らない
FR-06 案件属性を踏まえて優先度を付けられる Must 売上規模・顧客ランクを重視し、契約状況・要望件数・複数案件への広がりを補助的に加味する
FR-07 機能改修 / 追加の提案を出せる Must プロダクト情報を参照し、新規追加か既存改善かが分かること
FR-08 提案ごとに根拠を示せる Must 元の要望、参照した案件属性（売上規模・顧客ランク・契約状況等）、参照したプロダクト情報をたどれること
FR-09 レポートを保存できる Must 会議資料として共有できる形式
FR-10 実行の記録を残せる Should いつ・どのデータで実行し、どこで失敗したかを追える
FR-11 実行時の LLM API を切り替えられる Should コストや契約に応じてプロバイダ・モデルを変更できる（開発支援ツールとは別）
FR-12 優先度の重み付けを設定で変えられる Could 売上規模・顧客ランク・契約状況等の比率をチーム方針に合わせて調整できる

7. 非機能要件・制約

項目 内容
実装言語 TypeScript
起動方法 TypeScript の CLI から実行する
実行時の AI LLM API（OpenAI / Anthropic / Google 等）を直接呼び出す。コストを抑えられるモデルを既定とする
開発支援ツール 実装時は Cursor を推奨。Codex、Claude Code でも開発可能な構成とする（実行時の LLM とは別）
実行時間 会議前に実行して待てる範囲（数分程度）で完了する
データ量の想定 年間案件 300 件前後、要望 1200 件前後を上限の目安とする
コスト 週次実行を続けても負担にならないモデルを既定にする
失敗時の挙動 データ取得失敗や AI の応答不正時は、原因が分かる形で停止する。中途半端なレポートは出さない
再現性 サンプル同梱時は GitHub 上の架空データを同梱し、手順に沿えば作成者以外（第三者）でも同じ結果を確認できる
データの扱い サンプル同梱時は架空データをリポジトリに同梱する。実務利用時は顧客データと生成レポートを社内限定の共有環境で管理する（§5.1.1 参照）

セキュリティ

実務利用時の案件・要望データには顧客名、売上規模、契約状況といった社外に出せない情報が含まれる。 サンプル同梱時は架空データのみを扱う。扱いは次のとおりとする。

項目 内容
サンプル同梱時のデータ GitHub リポジトリ上の架空データ（案件・要望・プロダクト情報）を同梱する。実在顧客の情報は含めない
実務利用時の保管場所 顧客データと生成レポートは、GitHub や Google ドライブなど社内メンバーのみアクセスできる共有環境に置く。公開リポジトリや個人領域には保存しない
アクセス権 実務データの閲覧・編集できる範囲を社員に限定し、権限は共有サービス側の機能で管理する
認証情報 API キーは環境変数などデータ本体と分離した場所で管理し、リポジトリに含めない
AI へ渡す情報 分析に必要な範囲に限る。個人名や連絡先など不要な個人情報は渡さない
出力の扱い 実務利用時のレポートにも顧客情報が含まれるため、入力データと同じ社内限定の範囲でのみ共有する
実行記録 ログに要望本文や顧客名をそのまま残さない。追跡は識別子で行う

8. 完成基準と決定事項

8.1 完成の基準

次がすべて満たされた時点で、想定した業務に使える状態とみなす。

  1. TypeScript CLI から案件・要望・プロダクト情報を入力し、レポート生成まで止まらずに実行できる
  2. レポートにテーマ・提案（新規追加 / 既存改善の区別）・優先度・根拠・影響案件が含まれる
  3. 1要望につき主テーマ1つが付与され、表現が違う同じ要望が同一テーマにまとめられている
  4. 優先度が案件属性・要望件数・複数案件への広がりに基づいており、根拠を元の要望までたどって説明できる
  5. 新規追加 / 既存改善の判断がプロダクト情報（現行機能・方針・制約等）を参照しており、根拠にその参照が示されている
  6. API キーが未設定の場合に、秘密情報を出さずに失敗する
  7. サンプル同梱時: GitHub 上の架空データ（案件・要望・プロダクト情報）が同梱され、第三者が手順に沿って実行できる
  8. 実務利用時: 顧客データと生成レポートを、社内限定の共有環境で管理できる
  9. 想定ユーザー・使い方・制約・改善余地を第三者に説明できる状態になっている

8.2 決定事項

# 項目 決定内容 理由
1 起動方法 TypeScript の CLI から実行する 再現性が高く、CI や定期実行にも載せやすい
2 データの管理（サンプル同梱時） GitHub リポジトリに架空データ（案件・要望・プロダクト情報）を同梱し、第三者が実行できる状態にする デモ・検証に必要。顧客情報を含まない
3 データの管理（実務利用時） 顧客データと生成レポートを、GitHub や Google ドライブなど社内限定の共有環境で管理する 顧客情報を含むため、アクセス範囲を社内に限定する必要がある
4 開発支援ツール Cursor を推奨。Codex、Claude Code でも開発可能な構成とする 実装時の支援ツールであり、実行時の LLM とは別物として扱う
5 実行時の LLM LLM API（OpenAI / Anthropic / Google 等）を直接呼び出す。コスト優先のモデルを既定とし、切り替え可能にする 本要件を満たしつつ、運用コストを抑える
6 テーマ分類 1要望につき主テーマ1つ。必要なら関連テーマを補足する 分類の一貫性を保ちつつ、横断的な関連も失わない
7 優先度の重み 売上規模と顧客ランクを初期設定で重視し、契約状況・要望件数・複数案件への広がりを補助的に加味する 事業インパクトの大きい案件の要望を優先しつつ、横断的なニーズも拾う
8 プロダクト情報 入力データとしてプロダクト情報を持ち、新規追加 / 既存改善の判断に参照する 要望だけでは既存機能の改善か新機能かを区別しづらいため

8.3 運用しながら調整する項目

上記の決定を前提に、使いながら見直す想定の設定値。

項目 調整の観点
優先度の重み配分 売上規模・顧客ランクの比率、契約状況・要望件数・複数案件への広がりの加味度合い。実際の判断とのズレを見て調整する
対象データの範囲 1回の実行で扱う期間や件数。処理時間とコストを見ながら決める
テーマの粒度 まとめすぎ / 分かれすぎがないか。レポートの読みやすさを基準に調整する
実行時の LLM モデル 分類精度とコストのバランス。実行頻度が上がった場合に見直す
レポートの項目 会議で実際に使われた項目を残し、参照されない項目は削る
プロダクト情報の更新 機能追加や方針変更に合わせて、入力データをどの頻度で更新するか

本資料は要件定義。実装方式・システム構成・運用手順は別途、設計資料および README に記載する。
