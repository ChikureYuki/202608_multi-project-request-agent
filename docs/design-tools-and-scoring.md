# Function Calling と優先度スコア — 設計メモ

実装前に「何を設定すればよいか」を整理したドキュメントです。

---

## 1. Function Calling（ツール分割）とは

本エージェントでは **LLM がツールを 1 つ以上呼び出す** ことが前提です。  
「ツール分割」とは、エージェントが使える機能を **複数の独立した関数** として LLM に渡すことです。

### なぜ 1 つの関数にまとめないのか

| 分割する理由 | 説明 |
|---|---|
| 要件 | tool call ループ（複数回呼び出し）を示せる |
| 責務の分離 | 読込・計算・保存を分けるとテストしやすい |
| LLM の判断 | 「まず案件だけ読む」「次に要望を読む」など段階的に実行できる |

### 現在の設計（5 ツール — このまま実装で OK）

| ツール名 | 誰が実行 | 何をする | LLM が呼ぶタイミング |
|---|---|---|---|
| `load_projects` | プログラム | `projects.csv` を読む | 処理開始時 |
| `load_requests` | プログラム | `requests.csv` を読む | 処理開始時 |
| `load_product` | プログラム | `product_*.csv` を読む | 新規/改善判断の前 |
| `get_scoring_policy` | プログラム | `config/scoring.json` を返す | 優先度計算の前 |
| `save_report` | プログラム | HTML をファイルに保存 | 最終段階 |

**LLM がやること:** 上記ツールを順に呼び、返ってきたデータをもとにテーマ分類・提案文・根拠を生成する。

**あなたが決める必要があること:** 基本は **上記 5 つのままで問題ありません**。  
追加を検討するなら `compute_theme_scores`（スコア計算もツール化）程度。スコアはルール固定なので **プログラム側で自動計算し、LLM には結果だけ渡す** 方が安全です。

### 処理の流れ（イメージ）

```
CLI 起動
  → Runner が LLM に「レポートを作れ」と依頼
  → LLM: load_projects を呼ぶ
  → LLM: load_requests を呼ぶ
  → LLM: load_product を呼ぶ
  → LLM: テーマ分類・グルーピング（JSON 返却）
  → Runner: ルールでスコア計算（LLM に任せない）
  → LLM: 各テーマの提案文・根拠を生成
  → LLM: save_report を呼ぶ
  → 完了
```

## 2. 複数案件ボーナス — 現在の設定と意味

### ビジネス上の意図

**1 社だけの要望** より **複数社から同じテーマの要望が来ている** 方を優先したい、という要件（要件定義 §5.2 優先度・複数案件への広がり）に対応します。

### 計算式（確定案）

```
① 要望 1 件スコア = 利益ベース点 × 顧客ランク倍率 × 契約倍率
   利益ベース点 = clamp(round(annual_profit_yen / profit_yen_per_point), min, max)

② テーマ基本点 = ① をそのテーマの要望ぶん合計

③ 要望 3 件以上ボーナス:
   テーマ基本点 × 1.5   （実装前から backlog に載せたいイメージ）

④ 複数案件ボーナス（2 社以上）:
   ③ の結果 × (1 + 0.1 × (影響案件数 - 1))
```

### 具体例: 「CSV エクスポート」テーマ

要望 R001,R002（A 社）+ R003（B 社）+ R004,R005（C 社）+ R006（J 社）+ R007（D 社）+ R008（H 社・契約未済）= **8 件、6 社**

| 要望 | 案件 | 年間利益 | 計算 | 点数 |
|---|---|---:|---|---:|
| R001 | A (5,200万×A×契約中) | 52,000,000 | 100×1.2×1.0 | 120 |
| R003 | B (3,800万×A) | 38,000,000 | 76×1.2×1.0 | 91.2 |
| R004 | C (2,400万×B) | 24,000,000 | 48×1.0×1.0 | 48 |
| R008 | H (450万×C×**契約未済**) | 4,500,000 | 10×0.8×**0.3** | 2.4 |
| … | … | … | … | … |

（全要望を合計 → 例: 520 とする）

- 要望 8 件 ≥ 3 → 520 × **1.5** = 780  
- 案件 6 社 → 780 × (1 + 0.1×5) = 780 × **1.5** = **1170** → **高**

H 社は契約未済で 1 件あたり点が低いが、**件数と複数社ボーナス** でテーマ全体は上がる。

### config/scoring.json で触るパラメータ

| キー | 現在値 | 変えると |
|---|---|---|
| `profit_base_score.profit_yen_per_point` | 1000000 | 利益金額→ベース点の換算（100万円=1点） |
| `profit_base_score.min_base_score` / `max_base_score` | 10 / 100 | ベース点の下限・上限 |
| `multi_request_threshold` | 3 | 何件以上で「要望多数」扱いにするか |
| `multi_request_bonus_multiplier` | 1.5 | 要望多数ボーナスの強さ |
| `multi_project_bonus.multiplier_per_extra_project` | 0.1 | 2 社目以降 1 社あたり +10% |
| `multi_project_bonus.min_projects` | 2 | 何社以上で複数案件ボーナスを付けるか |
| `priority_labels` | 高≥150 / 中≥80 / 低≥30 | スコア → ラベル（確定） |

**あなたが決める必要があること:**

- 上記の **デフォルト値で試して、デモ後に調整** で十分です。
- 特に `priority_labels` の閾値（200/80）はサンプルデータで実行してから微調整が現実的です。
