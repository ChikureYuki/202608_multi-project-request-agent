作成したエージェントの利用シナリオ

どんなエージェントか

運用中のサービス・パッケージについて、複数案件の要望を横断整理し「次に何を作るか」を根拠つきで提案する TypeScript エージェントです。

誰が・いつ・何のために使うか

想定ユーザープロダクトマネージャー（PdM）
タイミング週次の優先度会議の前日〜当日朝
入力案件 CSV・要望 CSV・プロダクト情報 CSV（社内で管理）
出力HTML 提案レポート（テーマ・優先度・提案・根拠・影響案件）

業務の流れ（Before → After）

Before（手作業）
  • 案件ごとに要望を読み、表現の違いで同じ要望を見落とす
  • 年間利益・契約状況を頭の中で比較し、優先度が属人的
  • 会議前 1〜2 時間 を整理に使う
After（本エージェント）
  • CSV を置いて実行 → テーマ横断のレポートが 数分 で完成
  • 優先度付けはルール化を行い定量的に表現
  • レポートを読んで採否だけ判断する（約 5〜10 分）
Before
60〜120 分
要望整理・優先度の口頭調整
→
After
10〜15 分
実行 数分 ＋ レポート確認・採否 5〜10 分
週次あたりおおよそ 45〜105 分の短縮（会議前の整理工数）

サンプルデータの設定（デモ用）

  • プロダクト: MCP Manager（AI エージェント管理基盤）
  • 案件 10 件（株式会社A〜J）、要望 21 件（各案件 1〜3 件）
  • 未契約案件 2 件 — 契約前の要望はスコアを減少させて判断
  • 利益は帯区分ではなく 年間利益（円） — 100 万円 = 1 点でベーススコア算出

実際の動作

画面共有デモ — 以下の LLM モード手順で実行し、生成された output/report.html を見せます。

事前準備（評価者向け）

  1. .env.example を .env にコピー
  2. GOOGLE_API_KEY を設定（Google AI Studio で取得）
  3. npm ci --ignore-scripts && npm run build
  4. 入力 CSV を data/production/ に配置（デモは data/sample/ をコピー）

Windows: scripts\report.bat
Mac: ./scripts/report.sh

Gemini API でデータ読込 → テーマ分類 → 提案文生成 → HTML 保存

3

レポート確認

output/report.html がブラウザで開く

デモで見せるポイント（レポート側）

  1. サマリー表 — テーマ名・スコア・提案内容がスコア降順
  2. 「データのエクスポート機能」 — 8 件・複数社 → 優先度「高」、新規追加
  3. 根拠 — 要望 ID、年間利益・ランク・契約状況、プロダクト機能一覧を参照
  4. 監査ログ改善 — 3 件ボーナス、既存機能 F003 の改善提案

アーキテクチャと設計意図

アーキテクチャ

Tools は Runner の兄弟ではなく、Gemini の Function Calling（① 読込フェーズ）で Runner が実行する。Scoring と save_report は Runner が直接呼ぶ。

flowchart TD CLI[TypeScript CLI] --> Runner[Agent Runner] Runner <-->|① 読込 FC ループ
② 分類 · ④ 提案| Gemini[Gemini API
gemini-3.6-flash] Gemini -->|function call| Handlers[Tool Handlers] Handlers --> LoadTools["load_projects · load_requests
load_product · get_scoring_policy"] LoadTools --> CSV[(CSV data/)] LoadTools --> Config[(config/scoring.json)] Handlers -->|実行結果| Runner Runner --> Scoring[③ Scoring
ルールベース] Scoring --> Runner Runner --> Render[Report Render] Render --> Save[save_report
Runner 直接呼出] Save --> Output[(HTML output/)]

処理フロー（report.bat → LLM モード）

デモで実行する bat/sh は、以下の順序で処理します（並列ではなく段階実行）。

起動 · scripts/report.bat → cli.ts
data/production/ を指定して runAgent() を呼び出す。LLM モードでは .env の API キーを使用。
↓
Agent Runner · runner.ts（司令塔）
以降のフェーズを順番に制御。スコア計算と HTML 生成は Runner が直接呼び出す（LLM に任せない）。
↓
フェーズ 1 · LLM + Tools（データ読込）
Gemini が Function Calling で 4 ツールを呼び出し: load_projects · load_requests · load_product · get_scoring_policy
実処理は tools/handlers.ts（プログラム）が CSV / JSON を読む。
↓
フェーズ 2 · LLM（テーマ分類）
要望をテーマにグルーピング（表現が違っても同義をまとめる）。JSON で分類結果を返す。
↓
フェーズ 3 · Scoring（優先度算出）
scoring/calculate.ts が config/scoring.json に従いテーマごとのスコアを算出。LLM は使わない。
↓
フェーズ 4 · LLM（提案文・根拠）
スコア付きテーマごとに、新規/改善・提案文・根拠・参照プロダクト情報を JSON で生成。
↓
フェーズ 5 · Report Render + 保存
report/render.ts で HTML 化 → save_report で output/report.html に書き出し → ランチャーがブラウザで開く。
▸ 開く とじる 優先度スコア 要望ごとの利益・ランク・契約状況をもとにテーマ単位でスコアを集計し、高 / 中 / 低の優先度ラベルを付ける（config/scoring.json 準拠・LLM は使わない）。
STEP 1
要望 1 件のスコア

利益ベース点 × 顧客ランク倍率 × 契約倍率

利益ベース点 = clamp(round(annual_profit_yen ÷ 100万), 10, 100)　|　A/B/C = 1.2 / 1.0 / 0.8　|　契約未済 = ×0.3
STEP 2
テーマ基本点

そのテーマに属する要望スコアの合計

STEP 3
要望件数ボーナス

要望が 3 件以上 → テーマ基本点 × 1.5

STEP 4
複数案件ボーナス

影響案件が 2 社以上 → 上記 × (1 + 0.1 × (案件数 − 1))

STEP 5
優先度ラベル
高 ≥ 150 中 ≥ 80 低 ≥ 30

LLM API / ツール / データ保存の設計

LLM API（実行時）

  • Google Gemini API（デフォルト gemini-3.6-flash）
  • API キーは .env の GOOGLE_API_KEY のみ — リポジトリに含めない
  • 実装時の AI（Cursor 等）とは別物 — 実行時は Gemini のみ使用

ツール

ツール名動作の概要
load_projectsprojects.csv から案件ごとの年間利益・顧客ランク・契約状況・契約期間を取得
load_requestsrequests.csv から要望本文・紐付く案件 ID・入手元・記録日を取得
load_product現行機能一覧とプロダクト方針・制約を取得し、新規/改善判断の参照元にする
get_scoring_policy優先度の倍率・閾値ルール（scoring.json）を Runner / LLM に渡す
save_report生成した HTML レポートを指定パス（output/report.html）に保存

データ保存の設計

区分置き場所備考
本番想定（入力） data/production/ 社内限定。顧客名・利益・要望本文を Git に載せない
出力 output/report.html ブラウザ共有・議事録添付。生成のたびに上書き or 日付付きファイル名
CSV 設計意図: 列名・粒度は DB テーブルに移行しやすい構成（案件 ID・要望 ID 等の正規化）としています。初期は CSV で手軽に始め、セキュリティ要件や企業要望に応じて DB 直接参照 や スプレッドシート連携 に差し替え可能です。Tools の読込層だけ差し替えれば Runner / LLM の流れは維持できます。
▸ 開く とじる CSV 構成 各ファイルは DB テーブル相当。列を追加する場合、値に改行を含むときはダブルクォートで囲む（CSV 標準）。

projects.csv

— 案件（1行 = 1顧客案件）
カラム型キー必須説明
project_id文字列PK必須案件識別子（例: P001）
project_name文字列—必須案件名称（サンプルは株式会社A〜J）
period_start日付—必須契約開始日（YYYY-MM-DD）
period_end日付—必須契約終了日
annual_profit_yen整数—必須年間利益（円）。優先度スコアのベース算出に使用
customer_rankenum—必須顧客ランク A / B / C
contract_statusenum—必須契約中 / 契約未済

requests.csv

— 要望（1行 = 1要望）
カラム型キー必須説明
request_id文字列PK必須要望識別子（例: R001）
project_id文字列FK必須紐付く案件 ID（projects.project_id）
request_text文字列—必須要望本文（テーマ分類の入力）
source文字列—必須入手元（定例、問い合わせ等）
created_at日付—必須記録日
urgency文字列—任意緊度高の目印（高 / 空）

product_features.csv

— 現行機能（新規/改善判断の参照）
カラム型キー必須説明
feature_id文字列PK必須機能 ID（例: F001）
feature_name文字列—必須機能名称
description文字列—必須機能の概要

product_meta.csv

— プロダクト方針・制約（キー値形式）
カラム型キー必須説明
meta_key文字列—必須product_policy / quarterly_focus / development_constraint 等。同一 key の複数行可
meta_value文字列—必須方針・今期重点・開発制約の本文
リレーション: requests.project_id → projects.project_id。要望は必ず 1 案件に属する。プロダクト CSV は案件横断の共通マスタ。

Claude Code 等の AI 開発ツールをどう使ったか

区別: 開発時は主に Cursor で実装。設計相談に ChatGPT を利用。実行時の LLM は Gemini API（別物）。

開発フロー（Cursor 中心）

  1. 要件定義 HTML を正とする用語・完成基準を固定し、Cursor が AGENT.md 経由で参照
  2. 型 → スコア → Tools → Runner の順で実装Cursor でボイラープレート・CSV パーサ・テストを生成
  3. Gemini 接続・エラー対応Function Calling・モデル世代差の修正も Cursor で反復
  4. --dry-run で無 API 確認 → LLM で最終確認修正サイクルは dry-run、提出前に API 実行で品質確認
  5. デモ資料・要件定義を HTML 化README は提出要件として用意したが、発表・評価向けに読みやすい HTML を追加作成

ChatGPT の利用（設計相談）

  • 優先度ルールの式・ボーナス設計のたたき台
  • ツール分割（5 種）と LLM / ルールの分担境界の整理
  • サンプルデータの件数・未契約案件数などデモシナリオの調整

AI に任せたこと / 人が決めたこと

AI に任せたこと（Cursor 等）

  • ボイラープレート・CSV パーサ・HTML テンプレート
  • Gemini Function Calling のエラー対応コード
  • README・設計メモ・ランチャー script の下書き
  • ユニットテストの雛形

人が決めたこと

  • 優先度ルール（150/80/30、利益ベース、100 万円 = 1 点）
  • LLM とルールの分担 — スコアは必ずプログラム側
  • サンプル 10 案件・未契約 2・要望 1〜3 件の構成
  • 採否は人、CSV→DB 移行可能な列設計
  • 提出物として HTML 資料を整備する方針

詰まった点、妥協した点、改善したい点

分類内容
詰まった
  • AI エージェントの定義理解
  • 実行方法の策定
妥協
  • 優先度スコアの詳細設定
  • データ設計
  • 詳細設計書の作成
  • テスト項目書の作成
改善したい
  • サービス、顧客に合わせた優先度の定量化設計
  • セキュリティ面の設計、環境構築の見直し

実務投入するなら何を追加するか

  • 採択→実装→CI/CD の自動化 — 要承認機能
  • AI エージェント業務環境での実行環境
  • 役職・役割ごとの関連作業の自動化・ツール組み込み
    • 起票者 — 要望の追加、ヒアリング不足事項の確認
    • 責任者 — 課題の吸い上げ、優先度調整
    • 実装者 — 採択状況の確認、設計の検討、資料更新
